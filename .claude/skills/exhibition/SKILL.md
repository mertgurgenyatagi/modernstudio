# Exhibition

Produces one scrolling HTML page that shows many different designs of a single page of the app, side by side in order, so the user can pick one. It is built with the **hallmark** skill (`.claude/skills/hallmark/`); load and follow it for every design decision, the Floor and the sweep.

The designs differ in **layout and structure**. They share the project's **look** (fonts and palette). The look only varies when the user says so in the invocation.

## Arguments

Free text after `/exhibition`. Read it for:

| Argument | Meaning | Default |
| --- | --- | --- |
| page | Which page to design. One of the pages named in [docs/pages.md](../../../docs/pages.md): Mixer, Song, Drums, Bass, Rhythm Guitar, Lead Guitar, Keys. | none, see "No page given" |
| N | How many designs. | 20 |
| fonts | A font style or named fonts, e.g. "serif", "monospace", "Space Grotesk and Lora". | the decided fonts |
| palette | A colour palette or mood, e.g. "warm", "monochrome", "#1f3a5f accent". | the decided palette |
| anything else | Tone, density, light or dark, genre, and so on. Treat it as a constraint on every design. | none |

Whatever the user gives overrides the matching default. Anything left unsaid stays at its default.

## Step 1: Load the decided look

Read `docs/design.md` before anything else. It is the project's decided fonts and palette, and it follows hallmark's locked-system rule (a `design.md` overrides hallmark's dealt direction and themes, and every page shares it).

- **The file exists:** its fonts and palette are the defaults. Use them for all N designs, except where the user's arguments override them.
- **The file does not exist:** stop and ask the user for fonts and a palette before generating anything. Do not invent them, and do not pick them freely. If the user already gave both fonts and palette in the invocation, no question is needed.

Also read, for the page's content, every doc the page depends on (always [docs/pages.md](../../../docs/pages.md) and [docs/open-items.md](../../../docs/open-items.md), plus the docs that pages.md links for that page). A design shows only what the docs say the page contains. Do not add features, controls or numbers the docs do not describe, and never invent data.

## Step 2: Plan the N layouts

Before building, write the plan as a numbered list of N one-line layout ideas and show it in the reply. Each line names the structural idea, not the colour or font: where the controls sit, how the main area is divided, what leads, how dense it is. Rules:

- No two layouts may share the same main idea. If two would be hard to tell apart at a glance, replace one.
- Spread the range deliberately: dense and sparse, centred and edge-anchored, one panel and many, linear and gridded, controls above, beside or below, and so on.
- Respect the page's job. For a note editor the editor stays the centre of the page; for the Mixer the five channels and the master stay visible. Layouts vary around that, not by dropping it.
- Use the real layouts the docs fix. The string pages use strings, not a piano roll; Drums uses its five rows; Keys uses a regular piano roll ([docs/instrument-layouts.md](../../../docs/instrument-layouts.md)). Layout variety applies to everything around and inside those constraints, never to replacing them.

## Step 3: Build with hallmark

Run hallmark once for the whole exhibition, in its batch mode: do not ask hallmark's four questions, infer them from the docs and state the inferences in one line. The page is an app screen, so use hallmark's app-screen path.

Fix the look through tokens:

- Declare the fonts and palette once, at `:root`, from `docs/design.md` or the user's override. Every design reads those tokens. Hallmark's Floor still applies: no literal colour or `font-family` outside the token block.
- Do not let hallmark deal a theme or direction per design; the look is already decided. If the user overrides fonts or palette, apply the override to all N designs the same way (still one set of tokens). Only if the user asks for different looks across designs do the tokens vary, and then each variation is a declared theme block.

### Every design is hand made

The point of an exhibition is variety, so each design is written by hand, one at a time, as its own piece of HTML and CSS. This binds for every N and every kind of exhibition, including one where the looks (fonts and palette) vary.

- **No automated generation.** Do not write a script, template, loop, function, data table or any other program that emits the designs, or several of them at once. Do not write one markup skeleton and reuse it with different values. Do not build the page by filling a list of design objects.
- **No clone and tweak.** Do not copy one design and change its colours, spacing or a few elements to make the next. Each design starts from its own layout idea in the plan and gets its own markup structure and its own CSS rules.
- **Write them individually.** Add the designs to the file one at a time (or a few at a time at most, each separately thought out), with Write or Edit. Before writing each one, re-read its line in the plan and make it differ from the ones already written in structure, not only in size or order.
- **What may be shared:** the token block at `:root`, the page header, the frame around each design, and small base rules such as the reset. Nothing that shapes a design's layout is shared.
- **Self-check in the sweep:** if two designs could be produced from the same markup by changing only CSS values, one of them is not hand made. Rewrite it.

Page structure:

- One HTML file, one scrolling page.
- A short header: the page name, the number of designs, and the fixed fonts and palette in one line.
- Then the N designs in order, each in its own clearly framed section with a number and a short title. The frame is plain; do not draw a fake browser or OS window (hallmark Floor 11).
- Each design is a real, rendered layout of the page built from HTML and CSS, not a sketch or a screenshot. Controls may look interactive; the exhibition itself does not need working audio or state.
- Scope every design's selectors under its own section class (for example `.d07`) so the 20 layouts cannot affect one another. Each design has its own rules; they are not one shared rule set switched by tokens.
- Responsive: the page works at phone width without horizontal scroll, and each design adapts inside its frame.

## Step 4: Output

Write to `docs/exhibition/<page-slug>.html`, where the slug is the lowercase, hyphenated page name (`rhythm-guitar`, `mixer`). Create the folder if it is missing. If the file already exists, do not overwrite it: write `<page-slug>-2.html`, then `-3`, and so on.

## Step 5: Sweep

1. If Node is available, run `node .claude/skills/hallmark/scripts/sloplint.mjs <output> --render`. Fix every `FAIL`; fix or waive every `REFLEX` with a real reason, as hallmark requires.
2. Open the file in a browser with the Playwright MCP, take accessibility snapshots, and check the console for errors. Look at a few designs at desktop width and at phone width. Do not claim it renders until you have looked.
3. Check that all N designs exist, none is a near-duplicate of another, and each follows the docs for that page.
4. Check that every design was hand made (see "Every design is hand made"): no generator script was used, and no two designs share the same markup structure.

## Reply

Keep it short:

1. One line naming the audience as: the user choosing a design for this page.
2. The path of the file, the page, N, and the fonts and palette used (and which ones were overrides).
3. The numbered one-line list of the layouts, so the user can answer with a number.
4. Anything you assumed, or any gate you waived, in one line each.

Do not paste the HTML into the reply.

## No page given

Special handling for an invocation with no page, in particular on the `00-overall` branch, is **not yet defined**. Until the user adds it here, ask which page the exhibition is for, and do nothing else.
